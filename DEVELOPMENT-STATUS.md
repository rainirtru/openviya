# Статус разработки и следующие шаги

Сверено 17 октября 2026 года по исходникам, миграциям, документации поставки и истории Git. Новые тесты, обращения к VPS и проверки внешних сервисов в ходе этой сверки не выполнялись. Ранее записанные результаты проверок ниже отделены от наличия кода.

## Как читать планы

В [общем плане backend](openviya-backend/docs/implementation-plan.md) этапы имеют номера 0–8, в [техническом плане](openviya-backend/docs/technical-implementation-plan.md) — 0–15. Например, общий этап 3 объединяет технические этапы 4–5, а общий этап 4 соответствует техническому этапу 6. Поэтому утверждение «этапы 1–4 завершены» без указания плана некорректно.

Ниже используются номера **технического плана**. Наличие класса или тестового файла означает реализованный артефакт; закрытие этапа требует выполнения его критериев приёмки.

### Основания

- Схема: `openviya-backend/src/main/resources/db/migration/V1__…V6__…`.
- Trial: `TrialClaimService` ставит задание; в production-исходниках нет реализации `OperationJobHandler`. При включённом worker неизвестный вид задания переводится в ручной разбор `NO_HANDLER`.
- `SubscriptionActivationService` подтверждает локальное начисление; вызов после реального применения в 3x-ui ещё не подключён.
- `ThreeXUiClient` содержит только три GET-операции. Установка панели средствами Ops не добавляет backend-адаптер выдачи подписок.
- [Web README](openviya-web/README.md) прямо ограничивает кабинет чтением профиля/подписки и выходом; покупки и trial UI не подключены.
- [Отчёт развёртывания](ops/control/DEPLOYMENT.md) фиксирует ранее выполненные проверки VPS и Telegram. Это исторический результат, а не новая проверка текущего сервера.
- Целевое нативное развёртывание backend из плана и описанный ранее контейнерный стенд — разные состояния. Наличие скриптов не подтверждает завершённый переход на systemd.

## Сайт и инфраструктурное приложение

| Направление | Выполнено | Следующий критерий готовности |
| --- | --- | --- |
| Сайт и кабинет | Главная по референсу, слоган, Telegram-вход, профиль, подписка, начисления, CSRF/logout; публикация описана в отчёте | После backend-выдачи добавить trial и его статусы, затем покупку/устройства. Сейчас кабинета продаж нет |
| Ops: Windows | Реестр, SSH trust, туннели, DNS, мастер подготовки VPS и обслуживание | Приёмка актуальной сборки на реальном управляемом тестовом VPS; локальные проверки не доказывают работоспособность каждой панели |
| Ops: общий LAN-сервер | ASP.NET Core, PostgreSQL, шифрованное хранение, HTTPS/token/pin, очередь настройки и обслуживания, удалённый клиент, перенос локальных данных | Запуск Docker на втором Windows 11, два клиента, продолжение задания после закрытия клиента и восстановление после рестарта |
| Поставка LAN | Три коммита `963f4c8`, `6e53f29`, `e644590`; [pre-release ops-lan-v0.1.0](https://github.com/rainirtru/openviya/releases/tag/ops-lan-v0.1.0), клиент/сервер/инструкция/SHA-256 | Результаты приёмки записать с версиями, датой и ограничениями; до этого выпуск остаётся предварительным |

Сборка LAN-решения ранее прошла без ошибок и предупреждений. На другом ПК служба ещё не установлена. Локальные туннели, Terminal и hosts требуют доступа на каждом клиентском устройстве. Очередь инфраструктурного Ops-сервера **не является** коммерческой очередью Java-backend.

## Следующие шаги в порядке выполнения

### 1. Принять LAN-режим на втором Windows 11

- [ ] Закрепить IP, установить Docker Desktop/Linux containers и PowerShell 7; запустить [комплект по инструкции](ops/lan/QUICKSTART.ru.md).
- [ ] Подключить ПК и ноутбук, перенести профили и выбранные секреты, проверить повторный перенос и конфликт редактирования двух клиентов.
- [ ] На тестовом VPS проверить выполнение принятого задания после закрытия клиента; проверить рестарт сервиса и журнал незавершённого обслуживания.
- [ ] Сделать backup PostgreSQL вместе с ключом шифрования и проверить восстановление в отдельном экземпляре.

Результат: общее хранилище действительно работает с двух устройств; восстановление не теряет ключи и не повторяет опасную операцию без разбора.

### 2. Закрыть контракт 3x-ui для первого trial

- [ ] Зафиксировать версии центральной панели и тестовых нод, inbound ID, subscription origin/маршрут и доверие TLS.
- [ ] Сверить DTO, единицы времени/трафика/HWID и поведение readback с G01–G15; разрешить изменяющие операции только на изолированном стенде.
- [ ] Согласовать правила начала периода/компенсации задержки, гонки trial с покупкой и допустимой задержки отключения новых и уже открытых соединений.
- [ ] Определить контракт собственного subscription gateway и crypt5 для реальных поддерживаемых Happ-клиентов.

Результат: известны запросы, ответы и правила восстановления потерянного результата; записи в production-панель не нужны для разработки стенда.

### 3. Реализовать первый работающий доступ

- [ ] Ввести контракт записывающего 3x-ui адаптера и долговечные привязки подписка → клиент → node/inbound.
- [ ] Реализовать handler пробной выдачи: актуальное желаемое состояние → внешнее применение → readback → однократная локальная активация; неизвестный ответ сначала сверять.
- [ ] Реализовать subscription gateway OpenViya, передачу HWID, crypt5 и прекращение доступа.
- [ ] Подключить trial-действие и состояния ожидания/ошибки в кабинет только после готовности backend-пути.
- [ ] Проверить весь путь Telegram → trial → Happ, лимит 2 устройств, повторную заявку, истечение, отказ ноды и восстановление после потерянного ответа.

Результат: технический этап 5 принят на стенде; запрос trial перестаёт оставаться только записью `REQUESTED`.

### 4. Коммерческий контур

После первого рабочего доступа: утвердить цены → каталог/скидки/купоны → заказы → общий контракт платежного адаптера → Pally/Overpay → идемпотентные webhook и сверка → возвраты. Конкретный провайдер заменяется через этот контракт; сейчас готового переключателя провайдеров нет.

Результат: подтверждённая оплата единожды начисляет время, потерянный ответ не вызывает повторный платёж/возврат, неподтверждённый возврат не меняет доступ.

### 5. Завершить продукт и эксплуатацию

Устройства и синхронизация нод, Telegram-уведомления, административное API/кабинет, целевое развёртывание backend под systemd, мониторинг, внешние резервные копии и восстановление. Стендовые критерии и приоритеты нельзя заменять успешной сборкой.
