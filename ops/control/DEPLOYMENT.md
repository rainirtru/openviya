## Предыдущие изменения

Последующий HTTP 500 при Telegram-входе локализован по исключению PostgreSQL: `spring_session.principal_name` превышал varchar(100). `UserPrincipal` не реализовывал `AuthenticatedPrincipal`, поэтому Spring использовал полное строковое представление профиля как имя principal. Исправлено: имя principal — стабильный внутренний UUID длиной 36 символов. Обновление `session-principal` развёрнуто на VPS с сохранением предыдущего JAR и образа. Семь локальных тестов прошли; интеграционный тест локально пропущен из-за отсутствия Docker. Отдельная проверка внутри обновлённого контейнера на реальном PostgreSQL подтвердила сохранение UUID в индексе и восстановление полного SecurityContext из сессии. Диагностическая транзакция отменена, отсутствие тестовой сессии проверено. Полный вход в браузере требует новой попытки пользователя.

Сервер `31.44.7.93`: Ubuntu 26.04 LTS, amd64, 954 MiB RAM, добавлен swap 2 GiB. Назначение — backend и центральная панель; VPN-клиенты работают через отдельные ноды.

Установлены backend OpenViya 0.1.0-SNAPSHOT, PostgreSQL 18.6, официальный 3x-ui v3.10.2 и Caddy. JAR собран из текущих локальных исходников; SHA-256: `05daad0bf88fd5899901dc395c1533466cfffc3a66d5a009f13ac5c30ae55c3d`. Образы внешних компонентов закреплены digest в root-only `.env` сервера. Локальные базы и `.env` разработчика не переносились.

Подтверждено на VPS:

- Все шесть миграций PostgreSQL применились; backend readiness — `UP`.
- Владелец backend создан одноразовым bootstrap; bootstrap выключен, его credentials удалены из runtime environment. Пароль сохранён в закрытом `private/access.json`; требуется пользовательское завершение TOTP enrollment.

При последующей попытке получен `TELEGRAM_ACCOUNT_UNAVAILABLE` уже из обработчика успешного OAuth, до появления строки пользователя/identity в БД. Исходный обработчик не журналировал причину и удалял сессию при отказе, поэтому фактический тип ID из этого конкретного токена задним числом не установлен. Исправлена совместимость профиля: точное положительное ID принимается числом или канонической десятичной строкой в том же 52-битном диапазоне; `sub` не используется как замена. Лимиты текста приведены к Unicode code points, добавлен журнал этапа/типа отказа без значений профиля. 12 тестов транспорта, ID и пользовательской сессии прошли. Обновление `profile-compat` развёрнуто с сохранением предыдущего образа/JAR и сверкой библиотек/миграций; завершение реального входа требует новой попытки пользователя.

После первой попытки реального Telegram-входа выявлен `invalid_id_token` с причиной `Malformed Jwk set`: Telegram периодически отдавал gzip-ответ JWKS, который стандартный JDK transport не декодировал. Добавлена ограниченная по размеру обработка gzip для JWKS и обмена кода; сохранены стандартные OIDC-валидаторы и проверка RS256. Шесть регрессионных тестов прошли, включая отказ на неправильную подпись, issuer, audience и срок токена. Исправление развёрнуто на VPS; исходный JAR и образ сохранены для отката, библиотеки и миграции не изменены. Компилированные классы и ресурсы из проверенной сборки перенесены пакетом `oidc-gzip-update.zip` со сверкой исходного артефакта и хешей библиотек. Актуальная контрольная сумма — в серверном `app.jar.sha256`, метаданные обновления — `private/oidc-gzip-update.json`. После обновления readiness UP, начальный OIDC redirect проверен повторно. Проверка именно настроенного декодера на реальном Telegram JWKS прошла, намеренно поддельный токен отклонён. Пользовательскую авторизацию необходимо начать заново для завершения проверки callback/ID token.
