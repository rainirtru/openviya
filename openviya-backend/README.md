# OpenViya Backend

Бэкенд — модульный монолит на Java 25 и Spring Boot 4.1.1. PostgreSQL хранит состояние приложения и долговечную очередь операций. Внешние интеграции подключаются после подтверждения контрактов запросов, ответов, повторов и восстановления.

## Локальный запуск

1. Установите JDK 25 и Docker Desktop с включенным Linux container engine.
2. Скопируйте `.env.example` в `.env` и задайте локальный пароль базы данных.
3. Из этой папки соберите приложение и запустите приложение с PostgreSQL:

   ```powershell
   Copy-Item .env.example .env
   # Замените OPENVIYA_DB_PASSWORD в .env.
   .\mvnw.cmd --batch-mode -DskipTests package
   docker compose up --build
   ```

Приложение слушает порт `8080`. Flyway применяет SQL-миграции при запуске. Информация об API доступна на `GET /api/v1`; проверки liveness и readiness — на `/actuator/health/liveness` и `/actuator/health/readiness`. Readiness проверяет PostgreSQL, liveness от него не зависит.

Чтобы запустить только API-процесс вне Compose, перед запуском `java -jar target/openviya-backend-0.1.0-SNAPSHOT.jar` задайте `OPENVIYA_DB_URL`, `OPENVIYA_DB_USERNAME` и `OPENVIYA_DB_PASSWORD` для доступного сервера PostgreSQL.

## Конфигурация

Секреты задаются через переменные окружения или локальный игнорируемый `.env`. В `.env.example` находятся только демонстрационные значения. Пароль базы обязателен: приложение не стартует, если `OPENVIYA_DB_PASSWORD` не задан. Платежные и VPN-интеграции пока не настроены и не могут сообщить об успешной операции.

Для TOTP требуется отдельный 32-байтовый ключ `OPENVIYA_TOTP_ENCRYPTION_KEY` в Base64. Используйте секрет-хранилище окружения; ключ нельзя менять без процедуры ротации, иначе сохраненные TOTP-секреты не расшифруются. Локальный `.env` не включается в Git.

## Первичный вход владельца

Публичной регистрации сотрудников нет. Для первого запуска задайте `OPENVIYA_BOOTSTRAP_OWNER_ENABLED=true`, логин и одноразовый пароль длиной 16–72 байта UTF-8. При старте приложение создаст владельца в статусе `PENDING`, только с ролью `OWNER` и без активной сессии. Затем отключите bootstrap и удалите логин/пароль из окружения до следующего запуска: если владелец уже существует, оставленный включенным bootstrap остановит приложение.

Сайт сначала получает CSRF-токен с `GET /api/v1/staff/auth/csrf`, затем выполняет парольный вход, запрашивает TOTP enrollment и завершает его кодом. Только после подтверждения TOTP выдается серверная PostgreSQL-сессия. Восстановительные коды возвращаются один раз — сохраните их вне приложения. В production используйте HTTPS и `OPENVIYA_SESSION_COOKIE_SECURE=true`; меняющие запросы требуют CSRF-токен.

Управление сотрудниками доступно владельцу через `POST /api/v1/admin/staff`, `PUT /api/v1/admin/staff/{id}/roles` и `PATCH /api/v1/admin/staff/{id}/status`. Каждая операция требует CSRF и поле `reason`; изменения ролей/статуса отзывают активные сессии. Подробный контракт находится в `docs/api/staff-auth.md`.

Для аварийного восстановления существующего владельца используйте только на один запуск `OPENVIYA_OWNER_RECOVERY_ENABLED=true`, `OPENVIYA_OWNER_RECOVERY_LOGIN` и новый `OPENVIYA_OWNER_RECOVERY_PASSWORD`. Восстановление сбрасывает TOTP/recovery-коды, требует повторной настройки 2FA и отказывает, если для владельца оно уже выполнялось. Сразу после успешного старта отключите режим и удалите параметры с учетными данными из окружения. Режим восстановления нельзя включать вместе с первичным bootstrap.

Вход пользователя через Telegram Login/OIDC описан в `docs/api/telegram-auth.md`. Он выключен по умолчанию; для включения задайте BotFather client ID/secret, зарегистрируйте callback `{внешний origin backend}/login/oauth2/code/telegram` и укажите `OPENVIYA_TELEGRAM_OIDC_ENABLED=true`. Если приложение работает за reverse proxy и callback нельзя корректно вывести из запроса, задайте точный URI через `OPENVIYA_TELEGRAM_OIDC_REDIRECT_URI`. Пользовательский маршрут `GET /api/v1/me` доступен только после завершенного Telegram-входа.

Для отдельного доверенного Telegram-бота предусмотрен ограниченный endpoint разрешения идентичности. Задайте `OPENVIYA_TELEGRAM_BOT_SERVICE_TOKEN` как случайный секрет длиной не менее 32 символов отдельно в backend и bot service. Не используйте его в браузере; бот предварительно проверяет обновления средствами Telegram. Endpoint и контракт описаны в `docs/api/telegram-auth.md`.

## База и очередь операций

Схемой управляет Flyway; автоматическая генерация production-схемы Hibernate не включена. Первая миграция создает долговечную очередь с версией payload, уникальностью бизнес-ключа, арендами с истечением срока, монотонными поколениями аренды и отдельными индексами для готовых заданий, истекших аренд и ручного разбора. `OperationJobRepository` поддерживает повторное безопасное добавление задания, конкурентный захват через `FOR UPDATE SKIP LOCKED`, продление аренды и условные переходы в завершение, повтор или ручной разбор. Внешние вызовы следует выполнять вне транзакции базы, а результат записывать с поколением захваченной аренды.

## Контракты API

Ошибки API содержат стабильный код и correlation ID. Ответ возвращает проверенный входящий `X-Correlation-Id` либо создает UUID; детали серверных ошибок и ответы внешних систем клиенту не раскрываются. Контракты прикладных endpoint будут добавляться в `docs/api/` вместе с реализацией сценариев.
