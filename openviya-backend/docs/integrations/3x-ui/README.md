# Интеграция OpenViya с 3x-ui

Обновлено: 16 октября 2026 года. Статус: контракт для разработки адаптера. На настроенном пользователем стенде read-only запросы `GET /panel/api/server/status`, `GET /panel/api/nodes/list` и `GET /panel/api/inbounds/list` вернули HTTP 200 и `success=true`. Точный build панели/нод не зафиксирован; это не закрывает контрактные проверки изменяющих операций.

Документ дополняет [этап 5 технического плана](../../technical-implementation-plan.md#stage-5) и [этап 12](../../technical-implementation-plan.md#stage-12). Он описывает внешний API центра управления. Собственное API OpenViya для бота и кабинетов находится в [docs/api](../../api/README.md).

## 1. Источник и границы достоверности

Пользователь предоставил `openapi.json`; в проект сохранен [снимок спецификации](openapi.json): OpenAPI `3.0.3`, название `3X-UI Panel API`, `info.version = 3.x`, 184 пути, 55 схем компонентов. Проверены разбор JSON и разрешение всех 35 различных `$ref` внутри документа. Это не полная проверка соответствия стандарту OpenAPI и не проверка работающего сервера.

При сохранении заменено только значение `servers[0].url` на `/`: исходный индивидуальный путь панели не входит в документацию проекта. Реальный адрес задается конфигурацией. Остальное содержимое спецификации сохранено без исправления найденных противоречий; уточнения находятся в этом документе.

Исследование исходников v3.10.0 из технического плана остается отдельным источником: его выводы нельзя автоматически приписывать серверу, выгрузившему эту спецификацию.

## 2. Подключение и авторизация

- Административный API: настроенный HTTPS origin панели + ее базовый путь + путь `/panel/api/...` из таблиц ниже. Обеспечить однократное добавление base path и корректное кодирование path-параметров.
- Сервер подписок: отдельный настроенный HTTPS origin/base path; он может использовать другой порт и прокси. Шаблон `/{subPath}{subid}` не означает, что адрес строится от административного URL. Префикс и разделители проверить на конкретном развертывании.
- Для серверного адаптера предусмотрен `Authorization: Bearer <token>`. Также описаны `POST /login` и cookie `3x-ui`; поддержка cookie-входа не обязательна для первого адаптера.
- Есть несогласованность: вводное описание называет токен full-admin, а `POST /panel/api/setting/apiTokens/create` предлагает scopes `admin`, `monitor`, `node-sync`. Матрица разрешенных операций для scopes отсутствует. Не считать `node-sync` достаточным для управления клиентами без проверки G14.
- Служебный токен хранится в секретной конфигурации и используется только для разрешенных административных запросов. Он не передается в Happ, пользовательские DTO или публичные запросы подписки. У подписочных путей нет явного `security: []`, поэтому глобальный Bearer/cookie security формально наследуется; это пробел описания G08, а не основание требовать от приложения токен администратора.
- Не получать адреса для исходящих запросов из пользовательского ввода. Секреты и индивидуальный путь панели не добавлять в fixtures, примеры и диагностические логи.

## 3. Карта операций адаптера

Пути административного API указаны относительно настроенного базового пути панели. Наличие метода в таблице не означает, что его реализация уже существует в Java.

| Сценарий OpenViya | Метод и путь 3x-ui | Контракт и границы |
| --- | --- | --- |
| Проверить панель и локальное ядро | `GET /panel/api/server/status` | Состояние Xray и сервера; описание говорит о кэше с обновлением раз в 2 секунды. HTTP 200 сам по себе не подтверждает готовность продажи |
| Прочитать ноды | `GET /panel/api/nodes/list`, `GET /panel/api/nodes/get/{id}` | `NodeView`: status, enable, lastHeartbeat, xrayState, xrayError, configDirty, GUID и другие поля; определить свежесть и смысл полей на стенде |
| Актуализировать проверку ноды | `POST /panel/api/nodes/probe/{id}` | Обновляет сохраненное состояние здоровья; тело результата в схеме не типизировано |
| Найти доступные inbound | `GET /panel/api/inbounds/list`, `GET /panel/api/inbounds/get/{id}` | Сопоставить inbound с nodeId/originNodeGuid и разрешенными протоколами; учитывать enable и excludeFromSub. Не привязывать клиента ко всем inbound без проверки их назначения |
| Прочитать клиента и привязки | `GET /panel/api/clients/get/{email}` | Описание обещает inbound IDs и external config IDs, но `obj` не типизирован. Применяется для readback и восстановления неизвестного результата |
| Создать клиента | `POST /panel/api/clients/add` | JSON `{client, inboundIds}`, минимум один inbound. Секреты протокола могут генерироваться сервером; OpenViya заранее сохраняет стабильную идентичность для восстановления |
| Установить срок, статус, лимиты | `POST /panel/api/clients/update/{email}` | Полная замена клиентских полей, не PATCH. Описание обещает распространение на все привязанные inbound; результат по каждой ноде нужно проверить отдельно |
| Добавить новую доступную ноду | `POST /panel/api/clients/{email}/attach` | JSON `{inboundIds: [...]}`; после записи проверить состав привязок и применение |
| Убрать ненужную привязку | `POST /panel/api/clients/{email}/detach` | JSON `{inboundIds: [...]}`; намеренное исключение цели не смешивать с временной недоступностью ноды |
| Показать устройства | `POST /panel/api/clients/hwids/{email}` | Пример содержит id, firstSeen, lastSeen, userAgent, deviceOs, osVersion, deviceModel, fingerprint. `obj` не имеет строгой схемы |
| Освободить один слот | `DELETE /panel/api/clients/hwids/{email}/{id}` | Авторизация владельца подписки, суточный лимит и исключение поддержки выполняются в OpenViya; readback списка разрешает потерянный ответ |
| Прочитать агрегат слотов | `GET /{subPath}{subid}/hwid-status` | Только счетчики, без регистрации устройства; отдельный контракт сервера подписок. Не заменяет список устройств для кабинета |
| Получить содержимое подписки | `GET /{subPath}{subid}`, `HEAD /{subPath}{subid}` | Описание: Base64-ссылки; HTML при `Accept: text/html` или `?html=1`, JSON при `?format=info`. Собственный gateway сохраняет HWID-проверку и не открывает эти пользовательские страницы 3x-ui |
| Подготовить Happ crypt5 | `POST /panel/api/clients/happLink/{id}` | Целочисленный ID записи клиента; ответ `obj.encryptedLink`. Генерирует локально из текущего URL подписки клиента в панели. Подмена исходного URL параметром не описана; применимость к адресу OpenViya не подтверждена |
| Читать статистику | `GET /panel/api/clients/traffic/{email}` | Счетчики панели не становятся коммерческим источником периодов, цен или платежей |

Для административного подключения нод описаны `POST /panel/api/nodes/add`, `POST /panel/api/nodes/update/{id}`, `POST /panel/api/nodes/test` и `POST /panel/api/nodes/setEnable/{id}`. Секрет apiToken у ноды write-only: при update пропуск/пустая строка сохраняет прежний, `clearApiToken=true` очищает. `setEnable` по описанию управляет синхронизацией; не трактовать его как гарантированную остановку VPN на ноде. Эти операции выполнять только через полномочия сотрудников и аудит, если они включены в конкретный этап административного API.

`DELETE /panel/api/clients/hwids/{email}` очищает весь реестр: не использовать для обычного освобождения одного слота. Удаление клиента и массовые reset/import/bulk-операции не нужны для штатного продления. `GET /panel/api/clients/subLinks/{subId}` и `/links/{email}` возвращают готовые конфиги; не использовать их вместо HWID-gate подписочного сервера и не открывать пользователю.

## 4. Маппинг полей и сохранность идентичности

| Понятие OpenViya | Поле/форма 3x-ui | Правило адаптера |
| --- | --- | --- |
| Устойчивая внешняя идентичность | `{email}` | Служебный уникальный идентификатор, не обязательно почта пользователя. Создать и сохранить до первого POST; кодировать при подстановке в путь |
| ID записи панели | `ClientRecord.id`: integer | Отдельно от UUID; именно целочисленный ID требуется happLink |
| UUID протокола | `Client.id`: string; `ClientRecord.uuid`: string | Не смешивать с числовым ID записи. Сверить форму get/update; сохранять при повторе и продлении |
| Группировка подписки панели | `subId` | Стабильная привязка; не равна публичному токену OpenViya и не меняется при обычном продлении |
| Абсолютное окончание | `expiryTime` | В renewalPreview описаны Unix milliseconds, 0 = без срока, отрицательное = длительность с первого использования. Для коммерческого срока нужен положительный абсолютный момент после проверки G03; 7/30/... суток вычисляет OpenViya |
| Статус допуска | `enable` | Производный от права OpenViya; состояние поля не доказывает отключения открытой VPN-сессии |
| Лимит устройств | `limitHwid` | 2 для пробного, 5 для обычного. Поле присутствует в ClientRecord и примерах операций, но отсутствует в Client; это явный пробел G02 |
| Лимит IP | `limitIp` | Передавать 0 независимо от limitHwid, подтвердить отсутствие ограничения при смене сетей |
| Квота трафика | `totalGB` | В Client написано GB, в примере add 50 GiB представлены числом 53687091200. Не выводить единицы из названия поля. Режим без квоты и readback проверить; покупка трафика отложена |
| Нативное продление | `reset`, `resetDay`, `resetWeekday`, `resetMax` | Отключить механизмы продления панели и проверить результат. Ноль resetMax сам по себе означает отсутствие предела числа продлений, а не их отключение |
| Целевые привязки | `inboundIds` | Один клиент на всех подходящих доступных нодах; новые/восстановленные цели синхронизируются без нового коммерческого начисления |

Для update сначала получить текущую форму клиента и подтвердить все сохраняемые поля по G02. Выделить DTO чтения, создания и полной записи: `Client` и `ClientRecord` имеют разные типы/имена полей (`id`/`uuid`, `allowedIPs` array/string, `created_at`/`createdAt`). Нельзя просто сериализовать DTO чтения обратно или отправить только expiryTime и limitHwid. Сохранять существующие протокольные настройки, идентификаторы и привязки. Неизвестная новая форма ответа требует остановить опасную полную запись и уточнить маппинг.

## 5. Ошибки, повторы и подтверждение применения

Базовая оболочка — `success`, `msg`, `obj`. Для большинства нужных административных операций описан только HTTP 200, а `obj` остается `{}`. Успех не определяется одним кодом HTTP; `success:false` не доказывает отсутствие уже сделанных изменений. Каталог кодов ошибок и точная семантика частичного результата остаются открытыми G04–G05.

До реализации каждой изменяющей операции подготовить паспорт: устойчивый ключ объекта, записанное намерение, GET для сверки, способ сравнения результата, допустимость повтора и действия при неоднозначном состоянии. Идемпотентный ключ, ETag/If-Match и прием монотонной версии команды в нужных операциях не описаны. Их нельзя считать поддержанными.

1. До POST сохранить намерение и стабильную внешнюю идентичность в PostgreSQL; внешние запросы выполнять вне транзакции БД.
2. При тайм-ауте после add прочитать прежний `{email}`. Не создавать новый email/UUID/subId и не повторять POST вслепую. Конфликт идентичности сверять с собственной привязкой, а не присваивать существующего чужого клиента.
3. После update/attach/detach сверять желаемые абсолютные значения и привязки. Для продления не использовать повторяемый `bulkAdjust addDays`: потерянный ответ может дать лишние дни. Полную запись с абсолютным сроком тоже разрешать повторять только после проверки формы и возможных побочных эффектов.
4. После удаления HWID сверить конкретный ID в реестре; окончательно учитывать одну успешную операцию освобождения в OpenViya. Проверить поведение отсутствующего ID и конкурентной регистрации.
5. Хранить состояние применения по node/inbound. Наличие клиента в центральной БД и отсутствие ошибки HTTP не подтверждают доступ через ноду. Не смешивать readback центрального клиента и подтвержденный внешний эффект.
6. Использовать сериализацию изменений одной привязки и reconcile актуального состояния. Они дают восстановление после сбоя, но без поддержки панели не запрещают исполнение запоздавшего старого запроса.

Подтвержденная выдача хотя бы через одну доступную ноду допускает запуск периода по протоколу активации технического плана; остальные цели остаются в синхронизации. Если не выдано нигде, начисление ожидает, оплаченное время не расходуется. Отсутствие доказанного сигнала применения по ноде — G07, а не основание молча заменить этот критерий на HTTP 200.

## 6. Gateway подписки и Happ

Публичный маршрут OpenViya — `GET /subscriptions/{opaqueToken}`. Он проверяет собственную подписку и обращается к отдельному подписочному серверу 3x-ui. Не обходить регистрацию устройств прямым чтением массива конфигов административного API.

Передаваемые данные устройства из плана: `X-HWID`, `User-Agent`, `X-Device-OS`, `X-Ver-OS`, `X-Device-Model`. В параметрах операции подписки предоставленного OpenAPI этих заголовков нет; их формат, обязательность и ответы при отказе нужно подтвердить по G09. Не отправлять общий HWID бэкенда для всех пользователей. Проверить, что отсутствующий HWID и превышение лимита не дают альтернативный путь получения конфигов.

Не передавать произвольные query/Accept, HTML-представления и запросы `format=info`. Проверить Content-Type, тело, статусы отказа, метаданные и redirect headers. Не отдавать прямые ссылки панели через `Profile-Web-Page-Url`, `New-Url`, `Fallback-Url`, Location или тело ответа. Кэш не должен обходить HWID-gate. Проверка gateway дополняется сетевым закрытием прямых серверов 3x-ui.

В этой спецификации есть локальный генератор crypt5; описание обещает свежую ссылку, без сохранения и обращения к внешнему провайдеру, с ограничением исходного URL 8192 UTF-8 bytes. Это уточняет прежний план, где предусматривался внешний Happ API. Однако happLink берет текущий URL клиента панели и не документирует произвольный входной адрес. Нельзя считать, что метод уже подходит для `/subscriptions/{opaqueToken}` OpenViya.

Перед выбором реализации закрыть G11: проверить возможность сформировать ссылку именно на домен OpenViya без раскрытия прямого URL 3x-ui. Если метод панели этого не позволяет, отдельно подтвердить генератор Happ для собственного адреса. Выбор локального или внешнего генератора остается открытым; привязка к внешнему сервису не обязательна по одному наличию crypt5. Полученную ссылку сохранять в OpenViya и использовать при продлении, даже если генератор каждый раз возвращает новую.

## 7. Реестр пробелов и способ закрытия

Каждый пункт имеет статус **ОТКРЫТ** на 15.10.2026. «До реализации» относится к указанной части адаптера: не блокирует каркас, независимые операции и контрактные заглушки. Закрытие требует записать проверенную версию, обезличенный запрос/ответ или ссылку на конкретный исходный код и результат проверки; простого снятия checkbox недостаточно.

| G08 | GET подписки описывает Base64/HTML/info JSON, но схема ответа объявляет application/json с Msg; подписочные пути наследуют глобальную auth и единый servers | Уточнить отдельный адрес, prefix, HTTP-методы, реальную авторизацию, MIME, тело, статусы и заголовки. Не исправлять исходный снимок без пометки. До рабочего gateway; C06 |
| G09 | В операции подписки нет схемы HWID/метаданных устройства и отказов при отсутствии/превышении лимита | Проверить заголовки, кодировки/ограничения, все заявленные платформы Happ и отсутствие обхода через другие формы/headers. До подключения пользователей; C06–C07 |
| G10 | Список HWID типизирован только примером; нет полной семантики удаления отсутствующего ID, гонок, изменения лимита и повторной регистрации | Зафиксировать DTO, стабильность id, delete/readback, переход 2→5, уменьшение лимита, удаление при одновременном refresh. Проверить предел отзыва ранее полученного конфига. До пользовательского управления устройствами; C07–C08 |
| G11 | happLink генерирует crypt5, но не принимает URL OpenViya; поведение скрытия/экспорта в Happ не подтверждено API | Подтвердить источник URL и генератор, провести импорт/refresh на домен OpenViya и проверку UI Happ. До первого полного сценария; C09 |
| G12 | OpenAPI не доказывает автономное истечение, разрыв открытых сессий и границу задержки при отказе master/node-контроллера | Повторить исследование раздела 17.4 плана для выбранной сборки и измерить новые/открытые соединения. Требование окончания не ослаблять. До допуска к запуску; C10 |
| G13 | Не гарантированы автоматическая привязка старого клиента к новой ноде, состав подписки при исчезновении нод и восстановление целей | Проверить attach/detach, появление новой ноды и возврат старой; установить правила выбора обслуживаемых inbound без изменения коммерческого периода. До приемки синхронизации; C05 |
| G14 | Описание full-admin противоречит наличию scopes; матрица прав endpoint отсутствует | Проверить токены admin/monitor/node-sync, expiry/отключение, необходимые права без логирования секрета; закрепить рабочую конфигурацию. До эксплуатации административного адаптера; C01 |
| G15 | Отсутствуют контракт TLS/proxy конкретного размещения, гарантии скрытия прямых адресов, свежести кэша и недоступности native HTML/config путей извне | Проверить размещение, доверие TLS и gateway end-to-end: прямой доступ закрыт, query/header/redirect не открывают upstream, cache изолирован по устройству. G02–G04, G08–G11, G14 требуют уточнения формата или семантики перед завершением соответствующей функции. G05–G07, G12–G13, G15 требуют проверки внешнего поведения и размещения; наличие корректного DTO не закрывает их. Точный build G01 нужен для воспроизводимости всех результатов.

## 8. План контрактных и стендовых проверок

Обезличенные JSON fixtures проверяют маппинг и локальную обработку. Внешние эффекты проверяются отдельно на тестовой панели и минимум двух нодах; нельзя отмечать их проверенными по mock HTTP-серверу. Для сценариев недоступности и гонок стенд должен позволять управлять соединениями, ядром и node-панелью раздельно.

| ID | Проверка | Требуемое подтверждение |
| --- | --- | --- |
| C01 | Bearer/scopes, неверный/просроченный/отключенный токен | Фактические разрешения нужных endpoint и безопасный отказ; отсутствие token в пользовательских ответах |
| C02 | add → get → update → get | DTO, типы ID, единицы срока/трафика; full update сохраняет поля и идентичность |
| C03 | Пробный→обычный и продление | 2→5 без сброса устройств/URL; limitIp=0; абсолютный срок и native renewal не расходятся с OpenViya |
| C04 | Потерянный ответ, частичный отказ, старый update | Без дубликатов и лишних дней; известные границы частичного применения; исправление расхождения |
| C05 | Нода исчезла/появилась/восстановилась | Все подходящие доступные цели получают право, применение видно по целям, период не начисляется повторно |
| C06 | Подписка GET/HEAD и варианты Accept/query | Реальный host/path/auth/MIME/body/status/headers; рабочее содержимое поступает через OpenViya |
| C07 | HWID отсутствует, устройства до/сверх лимита, смена сети | Нет обхода регистрации/лимита; один аппарат не становится новым только из-за IP; проверить платформы Happ |
| C08 | Удаление ID, тайм-аут, два освобождения, refresh | Достоверный результат и одно расходование суточного разрешения; прочие устройства сохранены |
| C09 | crypt5 OpenViya на Android/iOS/Windows/macOS | Импорт и refresh через свой домен; обычный просмотр/экспорт закрыт в поддерживаемом UI; продление сохраняет ссылку |
| C10 | Окончание при исправном/отказавшем master и node-панели | Измерены новые и открытые соединения, восстановление после отказа и техническая задержка |
| C11 | Прямой upstream, HTML/info, redirects, metadata headers | Нет публичного обхода OpenViya и утечки служебного адреса/ссылок на конфиги |
| C12 | Кэш и конкурентные запросы разных устройств | Кэш не обходит gate, не смешивает пользователей/устройства и не продлевает истекшее право |

## 9. Порядок реализации и условия готовности

1. Закрепить G01, согласовать DTO и рабочую auth для нужных endpoint. Подготовить локальные fixtures и проверки C01–C03.
2. Реализовать чтение состояния, создание, полную запись и восстановление неизвестного результата. Проверить C04–C05; записать способ подтверждения применения по цели.
3. Реализовать gateway с сохранением HWID-gate, затем проверенный генератор crypt5 для собственного URL. Закрыть соответствующие G08–G11 и C06–C09.
4. Завершить пользовательское освобождение слотов, reconcile новых/восстановленных нод, сетевое закрытие upstream. Проверить C08, C11–C12.
5. Выполнить проверку фактического истечения C10 на выбранной сборке и зафиксировать условия допуска из технического плана. Не объявлять интеграцию готовой к эксплуатации по одному перечню API.

Для стенда позднее нужны точные версии панели/нод, адреса admin/subscription и их префиксы, разрешенные inbound, отдельный токен и настройки TLS. Секреты передаются конфигурацией при подключении, а не через этот документ. Сейчас дополнительные ключи и документы не требуются для продолжения проектирования.

При обновлении панели повторно выгрузить и обезличить спецификацию, записать новый hash и build, просмотреть diff используемых методов/схем и повторить затронутые C-проверки. Старые результаты не переносить на новую сборку автоматически.
