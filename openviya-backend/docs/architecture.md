# Архитектура бэкенда OpenViya

Форма приложения принята в обсуждении Q36, технический набор — в Q55. Решение о форме приложения записано в [ADR-0001](adr/0001-modular-monolith.md).

## Форма приложения

- Одно приложение на Java 25 LTS и Spring Boot 4.1.1, сборка через Maven Wrapper.
- Одна PostgreSQL-база; каждый внутренний модуль отвечает за свои данные.
- Изменения схемы базы выполняются миграциями.
- Бэкенд и база запускаются вместе через Docker Compose.
- Telegram-бот, пользовательский веб-кабинет и административный веб-кабинет обращаются к API бэкенда и реализуются отдельными модулями общего проекта.
- REST API обслуживает эти каналы, а состояние фоновых операций сохраняется в PostgreSQL.
- Коммерческие правила принадлежат OpenViya; особенности внешних систем находятся в отдельных адаптерах.

## Обязанности внутренних модулей

| Модуль | Ответственность |
| --- | --- |
| Учетные записи и авторизация | Пользователи, Telegram, будущий email; учетные записи сотрудников, 2FA и роли |
| Каталог предложений | Периоды, цены, скидка на первую покупку и купоны; основа для уровней подписки, дополнительных возможностей и пакетов трафика |
| Подписки | Пробный доступ, периоды, продление, остаток времени и права пользователя |
| Платежи | Заказы, ссылки, подтверждение оплаты, возвраты и выбор платежного провайдера по способу оплаты |
| Управление VPN-доступом | Выдача и восстановление, синхронизация сроков и лимитов, устройства, состояние центров управления и нод |
| Уведомления | Напоминания, сообщения о выдаче доступа и задержках; первоначально Telegram |
| Административные операции и аудит | Операции сотрудников с проверкой полномочий и записью того, кто, когда и что изменил |

## Адаптеры

- 3x-ui: взаимодействие с первым центром управления VPN-инфраструктурой.
- Pally: предпочтительная интеграция для СБП; основной контракт проверен по официальному reference и предоставленному HTML, hostname API и доступ к возвратам еще требуют подтверждения.
- Overpay: предпочтительная интеграция для карт; возможности конкретного магазина еще требуют подтверждения.
- Happ: подготовка подключения через crypt5.
- Telegram: связь пользовательского канала и уведомлений с бэкендом.

Возможности каждого центра управления описываются явно. Новый адаптер должен сохранять модель коммерческой подписки OpenViya, не переносить ее правила в поля конкретной панели.

## Обработка покупки

1. Выбор предложения и применимой скидки; выбор способа оплаты для заказа с ненулевой суммой.
2. Проверка готовности инфраструктуры, создание заказа с фиксированными условиями и резервирование примененного купона.
3. Для заказа с оплатой — получение платежной ссылки и проверка подтвержденной оплаты. Для заказа со скидкой 100% — подтверждение бесплатного заказа без платежной ссылки.
4. Расчет приобретаемого периода подписки.
5. Выдача или продление VPN-доступа через адаптер центра управления.
6. Уведомление пользователя; при сбое — сохранение незавершенной операции и повторные попытки.

Повторное уведомление об одной оплате не добавляет период повторно. Незавершенные операции сохраняются в базе и продолжаются после перезапуска приложения; взаимодействие с внешними системами учитывает возможность частичного результата.

Смена способа оплаты создает новый заказ в рамках одного оформления покупки; прежняя оплата должна быть закрыта или ее результат выяснен до выдачи новой ссылки. Поздняя оплата замененного заказа учитывается и передается владельцу для возврата, сохраняя одно начисление периода.

Каждый заказ связан со своим начислением времени. Полный возврат отменяет только неиспользованный остаток соответствующего начисления; частичный сохраняет срок по умолчанию. Изменения по возврату применяются после подтверждения его успешного завершения.
