# Параметры и решения для следующих интеграционных этапов

Сверка 17.10.2026: сайт, Telegram OIDC и read-only подключение панели уже описаны в [отчёте развёртывания](../../ops/control/DEPLOYMENT.md). Следующие пункты — перечень параметров для конкретного стенда, а не утверждение, что все они отсутствуют. Сначала используйте [актуальный статус и порядок работ](../../DEVELOPMENT-STATUS.md); секреты повторно передавать не требуется.

Сначала завершаем проверки фундамента и доступа, затем первый сквозной сценарий подписки через Telegram → OpenViya → 3x-ui → Happ. После его успешной проверки переходим к предложениям, ценам и купонам.

## 1. Telegram

Для теста нужен отдельный тестовый аккаунт Telegram, которым можно войти через OIDC и получить событие в тестовом боте.

- Числовой Telegram user ID тестового аккаунта (`telegramUserId`, часто называют `tgId`). Его можно передать как число или строку цифр; это идентификатор, не токен.
- Bot ID / OIDC Client ID и Client Secret из настройки Telegram Login через BotFather.
- Публичный HTTPS адрес backend и адрес сайта, который должен открыться после входа.
- Точный callback, зарегистрированный в Telegram: `https://<backend-host>/login/oauth2/code/telegram`. Если перед прокси путь или схема отличаются, сообщить точный URI.
- Подтверждение, что домен backend и origin сайта добавлены в разрешенные URL Telegram Login.
- Для отдельного тестового bot service — токен Telegram Bot API (`TELEGRAM_BOT_TOKEN`) только в окружении самого bot service. Backend напрямую его не использует.
- Межсервисный секрет для вызова bot service → backend: `OPENVIYA_TELEGRAM_BOT_SERVICE_TOKEN`, случайная строка длиной не менее 32 символов. Одинаковое значение хранится в backend и bot service.
- При проверке уведомлений позже понадобятся числовой `chat_id` тестового личного чата или тестовой группы и согласие получать тестовые сообщения.

Фактические переменные backend уже задокументированы:

```dotenv
OPENVIYA_TELEGRAM_OIDC_ENABLED=true
OPENVIYA_TELEGRAM_OIDC_CLIENT_ID=<BotFather OIDC Client ID>
OPENVIYA_TELEGRAM_OIDC_CLIENT_SECRET=<secret>
OPENVIYA_TELEGRAM_OIDC_REDIRECT_URI=https://<backend-host>/login/oauth2/code/telegram
OPENVIYA_TELEGRAM_BOT_SERVICE_TOKEN=<random secret, 32+ chars>
OPENVIYA_PUBLIC_BASE_URL=https://<public-site-host>
```

## 2. Тестовый 3x-ui и ноды

Нужен изолированный тестовый стенд, где можно создавать, менять и отключать только тестовых клиентов.

- Точная версия и build/commit центральной панели (master) и каждой ноды; сообщить, одинаковые ли они.
- Административный HTTPS origin панели, включая base path, если он есть. Пример формата: `https://panel.example.test/<prefix>/`.
- Отдельный API Bearer token. На первом чтении достаточно минимальных read-only прав. Для следующих изменяющих проверок понадобится отдельный временный токен с подтвержденными правами создания/чтения/изменения/отключения клиентов.
- Сертификат TLS должен проверяться backend без отключения проверки. Если используется собственный CA, сообщить способ доверия ему в тестовом окружении.
- Подписочный HTTPS origin и точный путь/префикс subscription server. Нужен шаблон URL, не ссылка конкретного пользователя с действующим `subId`.
- Список тестовых inbound: имена и ID, протокол, какие должны выдавать доступ. Не отправлять UUID или активные ссылки существующих пользователей.
- Инвентарь не менее двух тестовых нод: понятные имена, ID/GUID, URL и соответствующие inbound; указать, как отдельно остановить и восстановить ноду, панель и Xray для fault-тестов.
- Подтверждение, что стенд разрешает измерить срок, HWID и отключение тестового клиента, включая существующее соединение.

Текущие переменные клиента чтения:

```dotenv
OPENVIYA_3XUI_ENABLED=true
OPENVIYA_3XUI_ADMIN_BASE_URI=https://<panel-host>/<base-path>/
OPENVIYA_3XUI_BEARER_TOKEN=<secret stored locally>
OPENVIYA_3XUI_CONNECT_TIMEOUT=3s
OPENVIYA_3XUI_READ_TIMEOUT=5s
```

Сейчас клиент поддерживает только чтение состояния панели, нод и inbound. Не включайте изменяющие запросы для production-панели.

## 3. Happ и собственная ссылка OpenViya

- Публичный HTTPS домен OpenViya и маршрут, который будет отдавать подписку через backend.
- Подтверждение, что этот домен доступен извне тестовых устройств и сертификат TLS действителен.
- Версии Happ и ОС тестовых устройств: Android, iOS, Windows и macOS — перечислить только реально поддерживаемые платформы.
- Тестовые устройства минимум на двух платформах, чтобы проверить импорт, обновление конфигурации, HWID-регистрацию, превышение лимита и окончание доступа.
- Подтверждение, что в Happ можно проверить поведение crypt5-ссылки: импорт/refresh через домен OpenViya, а также отсутствие обычного просмотра или экспорта исходного URL в поддерживаемом UI.

Полную ссылку с пользовательским секретом `subId` не присылать в чат или документацию. Для теста создадим отдельного пользователя и ссылку на стенде.

## 4. Решения перед первым реальным начислением

Технический план предлагает следующие варианты; для каждого подтвердить рекомендацию либо написать свой вариант:

| Правило | Предлагаемый вариант |
| --- | --- |
| Начало периода при задержке применения | Однократно подтвердить активацию локально после успешного readback и компенсировать задержку по протоколу раздела 9.1.1 |
| Расходование времени и возвраты | Последовательно применять события; считать остаток по моменту подтвержденного локального применения |
| Совокупные частичные возвраты достигли 100% оплаты | Отменить оставшееся время исходного начисления; сохранение доступа оформлять отдельным компенсирующим начислением |
| Покупка пришла, пока пробная выдача еще не активирована | Поглотить ожидающую пробную заявку; уже активированный остаток сохранить |
| Фактическое прекращение VPN | Указать допустимую задержку отдельно для новых подключений и разрыва уже открытых соединений; зафиксировать поведение при отказе панели/ноды |

Эти ответы влияют на бизнес-поведение и должны быть подтверждены до соответствующих обработчиков. Они не нужны для чтения панели и подготовки безопасного read-only клиента.

## 5. Данные для этапа предложений и купонов

Можно прислать после успешного первого VPN-сценария, либо заранее зафиксировать как требования:

- Цена в RUB для каждого периода: 7, 30, 90, 180 и 365 суток. Если период временно недоступен, отметить его отключенным. Цены задавать точными суммами в рублях и копейках.
- Возможности каждого предложения. Если все одинаковы, подтвердить стандартные возможности и лимит 5 устройств.
- Процент скидки первой платной покупки и ее диапазон; предложенная безопасная граница — меньше 100%.
- При одинаковом размере скидки: предпочесть скидку первой покупки и сохранить купон либо выбрать другое правило.
- Подтвердить округление до копейки `HALF_UP` либо указать другой способ.
- Для каждого купона: код/кампания, процент, дата начала и окончания, общий лимит использований, разрешенные периоды, активен ли купон.
- Для подарочного купона 100%: фиксированный период из списка (7/30/90/180/365 суток). Пользователь не выбирает срок самостоятельно.
- Уточнить, кто и каким административным способом создает/отключает предложения, скидки и купоны.

Без утвержденных цен каталог нельзя включить для пользователей; их не следует угадывать.

## 6. Как передать значения безопасно

- Секреты (`TELEGRAM_BOT_TOKEN`, OIDC Client Secret, `OPENVIYA_TELEGRAM_BOT_SERVICE_TOKEN`, 3x-ui Bearer token, пароли) не отправлять в чат и не добавлять в Git.
- Задайте их в уже предусмотренном локальном игнорируемом `openviya-backend/.env` или в secret store тестового окружения. Файл `.env.example` содержит только имена и демонстрационные значения.
- В сообщении достаточно указать, что тестовый стенд настроен, перечислить версии, публичные URL, inbound/node ID и заполненные ID Telegram. Если среда недоступна из backend, сообщить адрес VPN/allowlist или способ временного доступа.
- Не присылайте production-токены и не выдавайте тестовому backend доступ к production-данным.
