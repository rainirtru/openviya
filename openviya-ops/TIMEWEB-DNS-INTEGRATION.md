# Интеграция DNS Timeweb Cloud

Основание: предоставленный `G:/openapi (1).json`, изученный 16 октября 2026 года. Реализованы клиент API, хранение настроек и интерфейс DNS. Запросы к реальному аккаунту и изменения DNS при разработке не выполнялись.

## Выбранное поведение

- **Автоматически** — режим по умолчанию для новых профилей. Имена вычисляются по роли, региону, номеру и зоне; сохранение сервера запускает создание отсутствующих поддоменов и DNS через API. Кнопка явно сообщает это действие. Конфликтующие записи не перезаписываются.
- **Вручную** — пользователь создаёт записи на сайте провайдера и вводит доменные имена в профиль. Приложение не создаёт DNS через API, в том числе при сохранении.
- Существующие профили и старые файлы импорта получают ручной режим с сохранением адресов. Открытие приложения, импорт и удаление профиля не запускают изменения DNS.
- При отсутствии токена профиль сохраняется; приложение сообщает, что создание DNS ожидает настройки подключения. Сохранение профиля и изменение DNS не являются одной транзакцией.

## Возможности API

Базовый адрес: `https://api.timeweb.cloud`. Авторизация: `Authorization: Bearer <JWT>`. Файл описывает именно Timeweb Cloud; наличие домена у регистратора Timeweb само по себе не доказывает доступность его зоны в этом API.

| Действие | Метод и путь |
| --- | --- |
| Проверить доступность домена в аккаунте и список поддоменов | `GET /api/v1/domains/{fqdn}` |
| Прочитать настройки NS | `GET /api/v1/domains/{fqdn}/name-servers` |
| Прочитать пользовательские записи | `GET /api/v1/domains/{fqdn}/dns-records?limit=100&offset=0` |
| Создать поддомен | `POST /api/v1/domains/{fqdn}/subdomains/{subdomain}` |
| Создать запись | `POST /api/v2/domains/{fqdn}/dns-records` |
| Изменить конкретную запись | `PATCH /api/v2/domains/{fqdn}/dns-records/{record_id}` |
| Удалить конкретную запись | `DELETE /api/v2/domains/{fqdn}/dns-records/{record_id}` |

Для создания поддомена `{fqdn}` — основной домен, `{subdomain}` — только относительное имя. Например: `/api/v1/domains/openviya.online/subdomains/usa-1`.

Для создания DNS-записи v2 `{fqdn}` — полное имя цели: `/api/v2/domains/usa-1.openviya.online/dns-records`. Параметр `domain-subdomain-fqdn-create-dns` прямо требует предварительного создания поддомена отдельным методом. Формат ответа v2 с вложенным `data` не следует копировать в тело запроса.

Тело создания A-записи:

```json
{
  "type": "A",
  "value": "203.0.113.10",
  "ttl": 600
}
```

Адрес в примере документационный; приложение должно использовать введённый пользователем IPv4. Для IPv6 используется отдельная AAAA-запись после явного указания работоспособного IPv6 сервера. SSH hostname нельзя без проверки подставлять в значение A-записи.

## Сценарий OpenViya

Для VPN_NODE с регионом `usa`, индексом `1` и заданным публичным IP планируются две A-записи:

| Назначение | Имя | Значение |
| --- | --- | --- |
| VPN | `usa-1.openviya.online` | Публичный IPv4 VPS |
| Панель | `panel-usa-1.openviya.online` | Публичный IPv4 того же VPS |

Для CONTROL используется `panel-control.openviya.online`; профиль APP не получает выдуманную панель 3x-ui. DNS не задаёт порты: VPN 443, панель 38471 и SSH 22 остаются параметрами сервисов и профиля.

1. Сохранить подключение к провайдеру и проверить доступ к конкретному домену чтением API.
2. Проверить настройки NS и фактическое обслуживание зоны. Успешная запись в неавторитетной зоне не означает изменения публичного DNS. Не менять NS автоматически.
3. Прочитать все страницы пользовательских DNS-записей, существующие поддомены и необходимые default-записи. Нельзя принимать только первую страницу за всю зону. Для default-записей в спецификации есть `GET /api/v1/domains/{fqdn}/default-dns-records`.
4. Сформировать предварительный план для точных имён: «уже настроено», «создать», «конфликт». Найденные CNAME, другая A/AAAA или несколько адресов требуют разбора; не дописывать второй IP поверх конфликта.
5. В автоматическом режиме при сохранении профиля либо отдельном применении плана создать отсутствующий поддомен, повторно прочитать его записи, затем добавить отсутствующую A-запись. Повторное чтение важно: создание поддомена может сопровождаться записями провайдера; этот эффект спецификация не гарантирует и не исключает.
6. Проверить результат чтением API и сохранить полученные record ID. Совпадающую запись не создавать повторно.
7. Отдельно проверить публичное разрешение DNS. Учитывать TTL и отрицательное кеширование, не обещать мгновенную доступность после POST.

## Границы операций

- Предварительный план привязан к профилю, домену и IP. Если профиль меняется, план пересчитывается.
- Повторное применение читает текущее состояние и пропускает совпадающие записи. POST нельзя безусловно повторять после timeout: запись могла уже создаться.
- DNS-пара VPN/панель не является транзакцией. При частичном выполнении показывать результат каждого имени и позволять продолжить после перечитывания состояния. Не удалять успешную запись ради скрытого «отката».
- При 401/403 показывать ошибку авторизации/прав; при 429 учитывать Retry-After, если он есть. Чтение допускает ограниченные повторы; неизвестный результат изменения требует сверки состояния.
- Изменение IP — отдельный план с прежним и новым значением, точным record ID и перепроверкой непосредственно перед PATCH.
- Удаление локального профиля не удаляет поддомены или DNS-записи.
- Сохранённый record ID может относиться к ранее существовавшей совпадающей записи. Наличие ID в локальном реестре не доказывает, что приложение создало запись, и не разрешает её удаление.
- Методы покупки/удаления домена, изменения NS, управления VPS и оплаты не включать в DNS-клиент.
- В спецификации нет достаточного описания разрешений токена, чтобы обещать ограничение конкретной зоной. Возможность такого ограничения нужно проверить в панели провайдера; права запрашивать минимальные из доступных.

## Хранение и интерфейс

Отдельный `TimewebDnsClient` с фиксированным HTTPS endpoint, timeout и отключённым автоматическим следованием редиректам для авторизованных запросов. DTO и нормализатор должны учитывать разные схемы чтения v1 и записи v2: в частности, `data.subdomain` в v1 описан как полное имя, в v2 — как относительное. Проверять принадлежность итогового имени выбранной зоне.

Токен вводится в маскированном поле настроек провайдера, хранится через DPAPI текущего Windows-пользователя и исключается из экспорта, журналов, сообщений об ошибках и командной строки. Для разработки и тестов токен реального аккаунта не нужен: используется подставной HTTP transport.

В автоматическом режиме сохранение профиля строит свежий план и создаёт отсутствующие записи; карточка также позволяет отдельно проверить и применить план. В ручном режиме создание через API отключено. Окно подключения провайдера показывает доступность зоны и состояние токена. Результаты API и распространения DNS отображаются раздельно.

Локальный hosts-helper намеренно направляет домен панели на `127.0.0.1` для SSH-туннеля. Отдельная проверка использует Cloudflare DNS-over-HTTPS и не разрешает проверяемое имя через системный resolver Windows. Это результат публичного рекурсивного резолвера с возможным кешем, а не прямой запрос авторитетному NS. Проверка запускается пользователем, не выполняется при сохранении и не требует токена Timeweb в ручном режиме.

Создание A-записей не устанавливает сертификат, не открывает порт и не запускает 3x-ui. Эти этапы остаются отдельными. Доступность TXT в API позволяет в дальнейшем спроектировать DNS-01, однако текущий bootstrap использует согласованный HTTP-01 через TCP 80.

## Проверки перед выпуском функции

Подставной transport проверяет пути и тела запросов, пагинацию, предварительное создание поддомена, дубликаты/конфликты, разные формы имён v1/v2, частичный успех, потерянный ответ POST, отмену и 401/403/429. Тесты также проверяют отсутствие токена в экспорте и ошибках. После этого нужна проверка на отдельном тестовом имени в доступной зоне реального аккаунта. Настоящий токен вводится локально, а не в чате.
